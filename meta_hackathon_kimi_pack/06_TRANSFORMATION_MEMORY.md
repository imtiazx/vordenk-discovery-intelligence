# Transformation Memory — Data and Evidence Rules

## Purpose

Transformation Memory is Vordenk's core data asset. It connects what people said, what the system inferred, what stakeholders confirmed, what decisions were made, and what must happen next. It is the foundation for later diagnosis, design, requirements, delivery, and value realisation.

## First data entities

Keep the initial schema small and extend only when the user workflow needs it.

### Engagement
- `id`, `name`, `objective`, `scope`, `created_at`, `updated_at`
- Optional synthetic industry/domain label and success measures.

### Session
- `id`, `engagement_id`, `title`, `started_at`, `ended_at`, `status`
- Source type, transcription status, processing status, and a clear indication of demo/synthetic data.

### Source segment
- `id`, `session_id`, `source_type`, `speaker` if available, `start_time` / `end_time` if available, `text_or_reference`, `artifact_reference`
- Store the minimum required information; avoid storing more audio or raw content than needed.

### Knowledge object
- `id`, `engagement_id`, `type`, `title`, `description`, `status`, `source_refs`, `created_at`, `updated_at`, `version`
- Types can include fact, process step, actor, system, rule, pain point, metric, assumption, question, risk, dependency, requirement, and design option.

### Process model
- `id`, `engagement_id`, `version`, `nodes`, `edges`, `source_refs`, `review_status`, `created_at`
- Each node/edge should reference source or knowledge-object IDs where practical.

### Decision
- `id`, `engagement_id`, `statement`, `owner_or_approver`, `decision_date`, `rationale`, `scope`, `supporting_evidence_refs`, `status`, `version`.

### Review event
- `id`, `object_id`, `action`, `previous_status`, `new_status`, `edited_value`, `actor`, `timestamp`, `comment`.

## The four statuses

- **Extracted:** information is present in a source but may not be true or validated.
- **Inferred:** model-generated or analytically deduced; display uncertainty and evidence.
- **Validated:** a person with appropriate context confirmed it, or a specifically documented rule did.
- **Decision:** an explicit human choice. Store decision-specific metadata, not just a confidence label.

Do not mark something Validated merely because the model expressed high confidence. Do not convert a question into a fact. A user may reject an inference; preserve the rejection/history rather than repeatedly reintroducing it without explanation.

## Source provenance

For every material model-produced object, preserve:
- source session and source segment or artifact ID;
- exact supporting excerpt or a stable reference where permitted;
- timestamps/speaker labels if supplied by transcription;
- whether the link is direct evidence or an inference built from several sources;
- extraction/synthesis run ID and time;
- review status, reviewer, and revision history.

At write time, validate that referenced source IDs exist in the provided context. Never let the model invent source IDs or citations.

## Contradiction handling

When statements conflict:
1. Store each statement and source separately.
2. Create a conflict record linking both sides.
3. Explain what appears to conflict and why it matters.
4. Generate a focused question for the consultant/stakeholder.
5. Do not silently choose the newest statement or the model's preferred version.
6. After a human decision, preserve the decision and evidence; unresolved disagreement remains visible.

## Process graph

Represent a workflow as structured nodes and directed edges. Example node types: activity, role, system, input, output, decision gate, and exception. Include evidence links and a validation state. Render the view from data; do not treat Mermaid/diagram text generated by a model as trusted without parsing or validation.

## Cross-session retrieval

For the hackathon, prefer a simple and understandable method:
- retrieve recently validated and unresolved objects for the same engagement;
- include relevant prior conflict/decision records;
- retrieve source excerpts explicitly needed for the current question;
- limit context to what the model needs;
- retain IDs throughout the process.

Add vector search only after simple retrieval is tested and insufficient. Do not let a generic vector store become the product's core differentiator.
