# Backlog and Acceptance Criteria

This is a prioritised starting backlog, not a claim that any feature is already implemented. Reorder based on actual progress and deadline.

## Epic A — Product shell and evidence input (P0)

### A1. Create engagement/session
**Acceptance:** user can create or open the demo engagement and identify the current session. State remains available after refresh if persistence is implemented.

### A2. Transcript input
**Acceptance:** user can paste or upload a supported synthetic transcript; input validation provides a helpful error for unsupported or oversized input; session/source IDs are assigned.

### A3. Meta API connection
**Acceptance:** a server-side call to a current Meta model succeeds in a controlled test; key is not exposed to browser/source control; error state is visible if the call fails.

## Epic B — Structured understanding (P0)

### B1. Versioned extraction schema
**Acceptance:** output has known types for processes, actors, systems, rules, pain points, assumptions, questions, decisions, and source references. Invalid payloads are rejected or safely retried.

### B2. Source-linked claims
**Acceptance:** important claims reference source IDs that exist in the current input or retrieved project memory. Invalid/missing IDs are flagged; the UI doesn't fabricate evidence.

### B3. Status labels
**Acceptance:** Extracted, Inferred, Validated, and Decision are visibly distinguishable. Model confidence never automatically promotes an item to Validated.

## Epic C — Discovery intelligence (P0)

### C1. Checkpoint synthesis
**Acceptance:** the UI displays current understanding, questions, gaps/assumptions, and conflicts. It is generated by the real Meta model call.

### C2. Follow-up question ranking
**Acceptance:** questions are specific to the given process and explain briefly why resolving them matters. They are non-redundant against already answered questions where feasible.

### C3. Process visual
**Acceptance:** diagram is rendered from a validated structured process representation, remains legible, and displays meaningful nodes/edges rather than a generic decorative image.

## Epic D — Human control and memory (P0)

### D1. Review action
**Acceptance:** user can validate/edit/reject/defer an extracted or inferred object. The action is saved and represented in history.

### D2. Cross-session update
**Acceptance:** new evidence in a second session is compared with relevant earlier objects. Seeded contradiction is shown with both sources; the app does not silently overwrite the first statement.

### D3. Persisted correction
**Acceptance:** after refresh, the review action remains. The next checkpoint consumes the reviewed state and does not treat rejected inference as an unquestioned fact.

## Epic E — Input expansion (P1)

### E1. Audio file transcription
**Acceptance:** a supported synthetic/consented audio sample is transcribed with Meta Muse Voice Transcribe; error states and transcript linkage are visible.

### E2. Live streaming transcription
**Acceptance:** optional. Microphone input is streamed through the documented Meta endpoint with appropriate permissions, reconnection/error handling, and timestamps/speaker data where supplied. If unreliable, remove from demo and document limitation.

### E3. Workshop visual/document context
**Acceptance:** optional. A synthetic slide/photo/PDF is processed using a supported Meta multimodal input route and linked as a source. The app surfaces disagreements between visual and conversational evidence for human review.

## Epic F — Submission quality (P0)

### F1. Evaluation set
**Acceptance:** at least a few synthetic test scenarios cover basic extraction, missing questions, contradictions, unsupported claims, and human correction. Actual results are recorded.

### F2. Public repo
**Acceptance:** clean `.env.example`, no secrets/private data, setup instructions and necessary disclaimers; repo is accessible to logged-out users.

### F3. Demo video
**Acceptance:** accessible 3-minute video shows actual features built during the hackathon and actual Meta model usage; no fake users/results.

### F4. Build log and documentation
**Acceptance:** daily log identifies new work created during the hackathon, with real commit hashes where available. README separates implemented, incomplete, and future capabilities.

## Cut line

If behind, protect all of A, B, C, D, and F. Cut optional image generation, SAM segmentation, partner-provider experiments, live streaming if it jeopardises the stable path, and all future lifecycle modules.
